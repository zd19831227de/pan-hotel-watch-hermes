# `get_ebk_period_read` 实战坑与三平台昨日对比口径（2026-09-16 实测）

## 一、入参 schema（与其它 EBK 工具不同）

- 必填：`data_kind`、`period`；`chat_id` 建议透传。
- **不接受 `response_mode`**：传了直接返回 `Input validation error: Additional properties are not allowed ('response_mode' was unexpected)`。其余 EBK 工具（joint / latest / calendar 等）都吃 `response_mode`，容易顺手带上——本工具不要带。
- **也不接受 `watch_group_key`**（2026-10-14 实测）：同样报 `Additional properties are not allowed ('watch_group_key' was unexpected)`。单店群已由 `chat_id` 解析，本工具不需要也不允许传监控组 key；从其它 EBK 工具复制调用模板时要把这个字段删掉。丢掉一次调用就少一次现读预算（每轮现读至多 2 次）。
- `data_kind` 枚举四个：`business`（经营）、`ranking`（排名）、`pyramid`（仅携程金字塔投放）、`flow`（仅携程流量数据，2026-09-16 起）。
  传其它值会被参数校验拒绝。`flow` 支持昨天/过去7天/过去30天（period=day/week/month）与自定义区间/range_preset；指标=访客量/转化率（含较上周同期+竞争圈平均）+ 曝光/下单/成交转化率（我的酒店 vs 竞争圈漏斗）。
- 日期：`period=day`（昨日）、`range_preset=last_week|last_month`、或 `date_from`+`date_to`（区间最多 31 天、不能含今天）。区间读取不落库，口径看返回的 `date_range`/`caliber`。

## 二、本工具读不到的东西（如实说缺口，别硬换工具）

- **美团/飞猪的流量周/月/区间维度**：`data_kind=flow` 仅携程经营报告（flowdata 页）提供；美团/飞猪带区间问流量会被后端拦截（reason 含「仅携程」），如实说明并退「昨日流量」实时快照口径（`read_ebk_datasets` 的美团曝光量/飞猪列表页曝光人数）。
- **携程竞争排名 + 自定义区间**：返回 `status=not_available`，`summary` 类似「竞争排名页自定义区间与目标不一致…请人工复核」（即使页面日期看起来就是目标区间）。
  兜底：不传区间、用 `period=week` 读页面原生「上周」四榜（预订订单量/预订销售额/在店间夜/出租率/APP详情页访客量/APP详情页转化率/PSI/点评分），回复时标注「上周口径」，不要含糊成 1—15 日区间。

## 三、三端联合分析卡在账号参数

`get_ebk_joint_analysis_context` 点名美团/飞猪/三端时，若不显式传对应 `*_platform_account_id`，返回：

```
meituan: {status: missing, reason: missing_platform_account_id}
fliggy:  {status: missing, reason: missing_platform_account_id}
```

正确顺序：
1. 先 `resolve_feishu_chat_context(chat_id)` 读 `ota_ebk_accounts.{ctrip|meituan|fliggy}.platform_account_id`；
2. 再调 `get_ebk_joint_analysis_context(platforms=[...], ctrip_platform_account_id=..., meituan_platform_account_id=..., fliggy_platform_account_id=...)`。

不要把「缺 platform_account_id 参数」说成「本店未配置美团/飞猪」——`ota_ebk_accounts` 里已经列出的就是已配置账号。请求刷新时该工具可能被路由改判为 `ebk_period_read`，此时按 period_read 作答即可（`refresh_before_analysis=true` 会被拒）。

## 四、三平台「昨天销售」口径不可相加（2026-09-16 实测）

同一句「三平台昨天销售」读到的是三套不同口径：

| 平台 | 页面 | 字段 |
|------|------|------|
| 携程 | 经营概览·昨日数据 | 离店销售额 / 离店间夜量 / 成交率 / 平均卖价（含上周同期与竞争圈排名） |
| 美团 | 交易分析·按日 | 销售额 / 支付订单数 / 销售间夜 / 入住间夜 / 入住金额 / 平均房价 / 成交率（页面每日 9 点更新） |
| 飞猪（诊断报告·日报） | 只给在店间夜 / 间夜单价 / 预订订单，**没有销售额字段** | |
| 飞猪（经营数据·昨日） | 在店数据（在店间夜/房费收入/间夜单价）+ 预订数据（预订间夜/预订收入金额/预订订单） | |

- 回复必须逐平台标口径与读取时间，给「量级参考」时不写成同口径对账，禁止直接相加当成总营收事实。
- 飞猪日报（诊断报告）页与经营数据页字段不同：前者只有 3 个字段、无金额；后者才有房费收入/预订收入金额。想问金额要点名飞猪经营数据，否则会被指「金额缺失」。
- 美团按日数据每天 9 点左右刷新，上午读到的昨日数就是最终值；下午再读不会变，别把它当成「读取失败」。

## 五、反复「刷新」但数据没变时

连续两次同样的读取请求（如「刷新，读取飞猪昨天的销售情况」重复两遍）：若返回的快照 `id` 与 `captured_at` 完全相同，说明拿到的是同一份数据（页面在该时点未更新），**不是漏读**。

正确表述：给出数字 + 「快照编号与读取时间与上次相同，说明该口径数据自上次读取以来未更新」，并说明下次可能要等页面固定更新时点（如飞猪日报次日更新、美团按日 9 点更新）。禁止为了让回复「有变化」而编造差异或改写口径。

## 六、时间戳换算实测

- `read_times` 常见带 UTC 后缀：`2026-09-16T04:14:59.780698+00:00` → 北京时间 12:14 / 12:16（+8）。
- `captured_at` 常见无后缀：`2026-09-16 15:20:28.982756` → 已是北京墙上时间，直接说 15:20，**禁止再 +8**。
- 同一轮回复里两种格式可能同时出现（飞猪 `captured_at` 无后缀、美团 `read_times` 带 `+00:00`），要分别处理后再并排展示，不要因为换算不一致让店长看到自相矛盾的时间。

## 七、自定义区间只回「区间汇总」，没有逐日明细（2026-10-14 实测）

`data_kind=business` 传 `date_from`/`date_to` 时，`sections` 只给**三块区间汇总**（预订 / 在店 / 离店），每块下面是区间合计的订单数、间夜量、销售额、成交率、平均卖价等——**没有逐日行**。

- 问「每天/逐日 X」时不要以为一次区间读取就能出日曲线：要么按单日逐个现读（会很快吃满每轮 2 次现读预算，先告知店长时间），要么把区间累计数折成**区间日均**并明确标注「区间日均，非逐日」。
- 折日均：日均订单 = 区间预订订单数 ÷ 区间天数；日均间夜 = 区间间夜量 ÷ 天数；日均销售额 = 区间销售额 ÷ 天数。**预订均价用区间预订销售额 ÷ 区间间夜量自算**，不要把「离店平均卖价」当成预订均价（两者口径不同，实测可差出 30% 以上）。
- 区间跨度上限 31 天、不能含今天；要覆盖 8 月 + 9 月 + 10 月这种多自然月，就拆成 2~3 次区间读取（每次占 1 次现读预算）。
- 同日试算三个区间的实例（携程）：按自然月拆成「上月 / 本月整月 / 本月至今」三个区间各读一次，回包分别给出预订订单数、间夜量、销售额的区间汇总；**具体数值每轮现读后自算，本文件不留存历史读数**。
