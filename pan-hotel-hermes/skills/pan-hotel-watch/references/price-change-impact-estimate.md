# 「提价/降价 X 元 → 进单/营收影响」测算配方（2026-10-14 实测）

## 一、触发问法

「如果所有房型价格提高 20 元，每天的进单会有什么影响」「按 8-10 月规律做个测算」「涨价 10 块会影响多少单」「降价 30 元能多卖几间」。

这类问法**不是**查价指令、也不是改价指令（SKILL.md 已明确「含测算/分析/影响/规律等开放问法不是查询指令，直接用数据工具作答」），**禁止** `dispatch_watch_feishu_event`、禁止手拼审批字段。

## 二、硬边界：系统里没有本店价格弹性

没有任何同店不同价的对照实验数据，也没有弹性系数表。所以：

- **禁止**给一个「会掉 X 单」的确定数字。
- 必须给**情景区间**，并在正文与图注里写明「弹性为情景假设值、非本店实测」。
- 可以给「反推的隐含弹性」作为参照，但必须同时说明它被季节/节假日混淆，不能当因果弹性。

## 三、取数（现读预算：每轮至多 2 次）

1. `resolve_feishu_chat_context(chat_id)` 拿绑定。
2. `get_ebk_period_read(data_kind=business, platform=ctrip, date_from, date_to)` 按**自然月**逐个读（区间上限 31 天、不能含今天）。跨 3 个月就拆 3 次，分两轮调用。
   - **该工具不接受 `watch_group_key`，也不接受 `response_mode`**——带上会直接参数校验失败，白丢一次预算。
   - 自定义区间**只回区间汇总，没有逐日行**（见 `ebk-period-read-quirks.md` 第七节）。
3. 要锚定「+20 元相当于现价的百分之几」时，可以看一眼本店公开页现价。注意 `get_competitor_latest_prices` / `get_competitor_price_trend` 的回包可能极大（实测 12 万 ~ 38 万字符）并在工具输出里被截断：**用尽可能窄的参数**（`hotels='本店'`、`metric=min`、`days=1`），并直接读回包开头那几条——不要为了「拿全」反复重调同一工具。
4. 群归档可作为交叉验证：`search_group_archive(date_start, date_end, query="实施")`。本店 2026-08-01~10-14 实测归档 0 条，如实说缺口即可，不要编。

## 四、算式

设：基准均价 `P₀`（= 区间预订销售额 ÷ 区间间夜量）、提价幅度 `d = ΔP / P₀`、价格弹性 `ε`（负数）。

- 进单变化率 `= ε × d`
- 日均订单 `' = 日均订单 × (1 + ε × d)`
- 销售额变化率 `= (1 + d) × (1 + ε × d) − 1`
- **盈亏分水岭 ε = −1.0**：弱于 −1（客人不太在意价）提价增收，强于 −1 提价减收。每个月算出来都在 −1.0 附近，是这类测算最好用的一句话结论。

情景档位固定用 `−0.5 / −1.0 / −1.5 / −2.0`，店长一眼能看出区间。

## 五、反推隐含弹性（参照，必须带混淆声明）

用月度对比反推：`ε ≈ (Δ日均间夜%) ÷ (Δ预订均价%)`。取连续三个自然月的「日均进单」与「预订均价」，若观察到「均价高的月份进单少、均价低的月份进单多」，即可反推出一组隐含 ε（本店历史实测落在 −1.8 ~ −2.9 区间，**具体数值每次现读后重算，本文件不留存历史读数**）。

**必须同时说**：这组关系被季节与节假日严重混淆（可能出现价高量也高），不能当因果弹性；它只能说明「本店客群对价格不迟钝」，以及给出一个偏保守（偏减收）的参照带。同比侧通常也有正有负，是否佐证「需求大盘偏弱」要用本轮现读的同比数字判断，不要凭印象下结论。

## 六、基准数一律现读，本文件不留档

三个自然月的「日均预订订单 / 日均预订间夜 / 日均销售额 / 出租率 / 成交率 / 预订均价」必须每轮用 `get_ebk_period_read` 现读后自算，**本文件不保存任何历史读数**（避免拿旧数字当现状报给店长）。

自算口径：

- 日均预订订单 = 区间预订订单数 ÷ 区间天数
- 日均预订间夜 = 区间间夜量 ÷ 区间天数
- 日均销售额 = 区间预订销售额 ÷ 区间天数
- 预订均价 `P₀` = 区间预订销售额 ÷ 区间间夜量（不要用「离店平均卖价」顶替）
- 出租率 / 成交率 直接取回包字段，不自行推算

拿到 `P₀` 与区间日均订单后，`d = ΔP / P₀` 决定「+20 元相当于现价的百分之几」，再按第四节算式逐档算出日订单与日销售额变化，档位固定 `−0.5 / −1.0 / −1.5 / −2.0`。

**数字会随月份变，每次都必须重新现读，禁止沿用任何历史读数作答。**

## 七、交付形态

属于「区间报告 + 多行明细」（三个月 × 多情景），按大输出规则处理：

1. `send_operator_document(doc_type="pdf", title=..., content=markdown)` 发测算报告，章节＝结论速览 / 实际规律（表）/ 测算方法（写明无实测弹性）/ 每日进单影响（表）/ 分月测算（表）/ 本店自身价量关系 / 建议 / 数据缺口。
2. 本地 matplotlib 出一张图（左：月度均价×日均进单双轴，说明「价低量高」；右：弹性→日订单与日销售额曲线，标出 ε=−1.0 分水岭），`MEDIA:<绝对路径>` 一起发。配方与字体校验见 `local-chart-delivery.md`。
3. 群里只留 3~4 条结论，不复述报告表格。

## 八、结论怎么落（实测最有用的一段话）

- 不宜全房型一次性 +20 元：按自身历史反推的 ε（−1.8 ~ −2.9），日进单和日销售额都存在明显下行区间，具体幅度用本轮现读的日均订单算。
- 要试就小步：先挑 1~2 个主力房型或部分日期 +20 元，观察 5~7 天的进单与**成交率**（成交率是提价最直接的受损环节，观察值以本轮现读为准）再决定是否铺开。
- 出租率若明显低于全店目标且仍有空房冗余（用本轮现读的出租率判断），20 元的绝对金额不大，属可试探量级——这句能防止店长把测算读成「一动就崩」。

## 九、Pitfalls

- 别把「离店平均卖价」当基准均价：必须自算「预订销售额 ÷ 预订间夜量」。
- 别把区间汇总说成逐日数据；店长问「每天」时如实说明需要单日逐个现读。
- 别用 `dispatch_watch_feishu_event` 或任何写价/审批工具碰这类问法。
- 别省略「非实测弹性」声明——这是这类测算唯一会被追责的点。
- 别因为一次测算就调价：测算只给建议区间，执行链路见 SKILL.md 第 4 节。

## 十、店长重复发同一条测算请求（2026-10-14 实测连发 2 次）

同一句测算请求在一个会话里被连发两次是常态（历史记录里最多连发 4 次）。**不要**回「已发过」、也不要只把上一轮结论复述一遍：

1. 重新 `resolve_feishu_chat_context`，再把三个自然月区间全部 `get_ebk_period_read` 重读一遍。历史区间数字本身不会变，但重读既满足「报告数字来自本轮工具结果」，也证明没有沿用旧数据。3 个区间要**分两轮**调用（每轮浏览器现读预算 2 次）。
2. 重读结果与上一轮逐字一致时，**在回复里明确写「本轮已重新现读核对，数字与上次一致」**——店长重复问通常是因为没看到 / 想确认，这句话比再贴一遍数字有用。
3. 重新 `send_operator_document` 发报告，并重新带 `MEDIA:<绝对路径>` 发图。数字一致时图可以直接复用本会话已生成的那张 PNG，不必重画；报告要本轮重发，因为文档 content 必须来自本轮取数。
4. 群里依然只留 3~4 条结论，不要因为「第二次」就写得更长。
