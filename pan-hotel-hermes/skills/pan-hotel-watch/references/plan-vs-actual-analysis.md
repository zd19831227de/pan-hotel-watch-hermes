# 目标计划表（铺排表）对照实际经营：方法与口径

触发问法：「分析一下这份报表」「这份铺排表完成得怎么样」「缺口在哪」「按计划还差多少」——
用户把月度销售计划 / OTA 每日目标铺排表（xlsx 或截图）发进群。

## 第一步：先把目标口径拆出来并自检

从附件里取：月客房收入、月总间夜、OCC、ADR、OTA 占比、逐日计划间夜与均价。

自检（必做，报表经常不自洽，自检结论本身就是交付内容）：

- 总间夜 × 平均 ADR ≈ 客房收入？常见偏差：表头 ADR 与「客房收入 ÷ 总间夜」倒推值不一致（实测曾出现差 4%）。
  两个口径都要算出来给店长，说明本表按哪个执行、差多少金额。
- 每日「计划间夜 × OTA 占比」四舍五入后合计 与 总间夜 × OTA 占比 是否一致（差 2 间夜属正常取整）。
- 三端间夜拆分合计 = OTA 总间夜。
- 三端结构假设来自哪个月份的实测，要在回复里写明。

## 第二步：读同区间真实数据对照

`get_ebk_period_read(data_kind="business", period="day", date_from=..., date_to=...)`
一次拿到三平台同区间经营（现读，计入每轮现读预算；区间不能含今天、最多 31 天）。

## 第三步：口径分开算（这一步最容易答错）

| 要看什么 | 用哪个口径块 | 字段 |
|---|---|---|
| 金额进度（销售额达成率） | 携程「预订」块；美团「经营表现·销售间夜/销售额」；飞猪「预订数据」 | 预订间夜/预订销售额/预订收入金额 |
| 量与出租率 | 携程「在店」块；美团「入住间夜/入住金额」；飞猪「在店数据」 | 在店间夜、紧张度、出租率、间夜单价 |

**禁止把两口径混在一起算达成率。** 混用会同时得出「在店间夜已超 OTA 目标」和
「销售额只完成一部分」两个看似矛盾的结论——它们其实都对，只是一个看量、一个看价。
回复里要明确写「按预订口径…」「按在店口径…」。

**携程「在店」块没有销售额字段**，只有间夜量/紧张度/出租率 → 三端在店销售额无法合成，
这是真实数据缺口，如实说明，不要用离店销售额或预订销售额顶替。

## 第四步：缺口后压重算（最有价值的结论）

前 N 天少收的钱会**全部**压到剩余天数：

```
剩余需完成金额 = 月目标 − 已完成
剩余需完成间夜 = 月目标间夜 − 已完成间夜
剩余日均销售额 = 剩余金额 ÷ 剩余天数
剩余所需均价   = 剩余金额 ÷ 剩余间夜    ← 与原表剩余日均价对比，给出涨价幅度 %
```

原表给的「剩余日均」是**按计划应完成**算的，不是按实际缺口算的，直接引用会严重低估压力。

## 演算示例（数字全为虚构，只示范算法；真实数字必须每轮现读）

- 计划：某月客房收入 1,000,000 元 / 3,000 间夜 / OCC 75% / OTA 占比 60%
  → OTA 月目标 1,800 间夜、60.0 万元、均价 333 元；若表头 ADR 写 320（倒推 333，差 4%）。
- 1-9 日计划：600 间夜 / 20.00 万元（隐含均价 333 元）。
- 1-9 日实际（现读，写明读取时间）：
  - 预订口径：携程 450 间夜 / 15.00 万、美团 60 / 2.00 万、飞猪 60 / 2.00 万
    → 合计 570 间夜 / 19.00 万元；间夜达成 95.0%，金额达成 95.0%，缺口 1.00 万元；
    实际均价 333 元 vs 计划 333 元 → 本例量价同步。
  - 在店口径：携程 520、美团入住 55、飞猪在店 45 → 三端 620 间夜（携程出租率 65.00%，
    可用 120 间 × 9 天 = 1,080 房晚校验）。
- 重算后：剩余 21 天要 41.00 万元 / 1,200 间夜 → 日均 1.95 万元、均价需 **342 元/间夜**，
  与原表剩余口径对比给出涨价幅度 %（原表按「计划该完成多少」倒推，未计入已发生的缺口）。
- 结论式表述：先判断缺口出在「量」还是「价」——间夜按计划完成而销售额明显落后 = 价的问题；
  两者同步落后 = 量的问题；再用携程平均卖价与去年同档对比，说明是否在拿去年价格锚定今年。

## 输出组织

按「结论 → 依据（关键数字 + 口径 + 读取时间）→ 可能原因 → 建议 → 数据缺口」压缩到两屏内：

- 结论一句话点出是量还是价的问题。
- 依据给计划值 vs 实际值成对出现，每条带口径。
- 可能原因标注「判断，未证实」（例：计划按去年价格锚定、淡季比计划来得更早）。
- 建议给可执行的人工动作（目标下修 / 高价间夜往周末五六集中 / 按实际三端结构重算），
  只给参考区间，禁止任何执行性表述。
- 数据缺口写清「缺哪块、怎么补」。

用户已持有原件，这类问题**默认用短文字回答**，不要为出文件而出文件；
用户明确要文件或结论超两屏时才 `send_operator_document`。
